Follow-up review building on the original review package added in commit
`bb2dc7f` ("Add BTQ architecture review package"). The original predates the
field-capture pipeline, the markdown vault layer, the CouchDB integration
(Codex prompts 01–10), VPS provisioning, photo vision sidecars, and site
issue tracking. This review focuses on the new surface area plus a re-check
of the original review's findings against current code.

## Method

- Four parallel subagent reviews against the live tree:
  1. CouchDB integration layer
  2. Field capture pipeline (post-`bb2dc7f`)

  4. Cross-cutting concerns: tests, observability, deployment readiness
- Each agent returned file:line evidence; the most alarming claims were

- Baseline: `architecture_review_findings.md` (commit `bb2dc7f`).

## Verified-out claims

Two agent claims did not survive verification and are recorded here so future
reviewers don't re-flag them:

- **Token "leak" in `/api/session` JSON via `viewer_url`.** The
  `viewer_url` echoes the same token the client just authenticated with.
  Server logs are sanitized via `sanitize_token_text` at
  `project/field_capture/server.py:111`. This is not a regression; the
  query-param token model is documented in the roadmap. Browser-history
  exposure is a known design tradeoff, not a leak.
- **`default_field_capture_job` "auto-stages site issues without review".**
  Wrong. `plan_approved_job_draft` at
  `project/field_capture/approved_job_drafts.py:592` explicitly checks
  `candidate.status == STATUS_APPROVED` before draft generation, and drafts
  still require explicit staging to become queue jobs. The review boundary
  is intact.

## Findings — High Priority

These warrant attention before the next round of roadmap work.

1. **State-field naming mismatch (CouchDB).**
   `project/field_capture/couchdb_watcher.py:18` defaults to
   `DEFAULT_STATE_FIELD = "btq_state"`, but the listener tests and the Stage
   E roadmap use `"processing_state"`. Listener document queries depend on
   the field value. Silent-failure risk: a document with one field but not
   the other looks "pending" forever or never gets claimed. Both Stage E
   and CouchDB-review agents flagged this independently.

2. **`mark_processing` failure silently drops documents.**
   `project/field_capture/couchdb_watcher.py:88-90` `continue`s on failure,
   leaving the document as `pending` in CouchDB but unprocessed by this
   cycle. No retry, no backoff, no alert. Pair with exponential backoff +
   bounded retry, and surface persistent failures in the ops dashboard.

3. **Stage B cleanup (registry migration not finished).**
   - `SITE_VISION_CONTEXTS` dict still in
     `project/field_capture/photo_vision.py:135`.
   - `project/event_pipeline/sites.py` falls back to hardcoded `SITES` list
     when `CouchDBRegistryError` is raised, instead of failing closed with a
     logged error. Roadmap is explicit: "stale-but-routing is worse than
     skipped."
   - Vision path reads `SITE_VISION_CONTEXTS` directly instead of querying
     `CouchDBSiteRegistry.get_vision_context(site_id)`.
   - Operator docs (queue authoring guide, runbook) still point to the
     Python registry as the place to add sites.

4. **`add_person` idempotency window.**
   `project/queue_processor/main.py:1765-1766` writes the person file, then
   appends to the idempotency ledger. A crash between those two lines means
   retry hits `ensure_person_does_not_exist()` and fails. Smaller than
   pre-resolution windows but the only new handler with this exact gap.

5. **`_last_seq` advancement on heartbeats.**
   `project/event_pipeline/couchdb_listener.py:85` only advances
   `_last_seq` when a decoded change includes a `seq` field. A heartbeat as
   the last line before disconnect leaves `_last_seq` stale, causing
   re-processing of older changes on reconnect. Behavior is idempotent
   overall but wasteful and confusing in logs.

## Findings — Medium Priority

Real tech debt; can be addressed in passes alongside other work.

1. **`MarkdownVault` is read-only.** Introduced at
   `project/markdown_vault.py:14-100` to centralize vault operations, but
   queue handlers still call `atomic_write_text` directly with their own
   path construction. The abstraction never finished its journey. Could
   absorb writes incrementally as handlers get touched for other reasons.

2. **VPS pull relay is becoming dead code.** `vps_pull.py` exists because
   of the iCloud→VPS sync architecture. Once the SPA writes directly to
   CouchDB, this module becomes obsolete. Not currently gated, not flagged
   for removal. Plan a deliberate decommission tied to SPA→CouchDB cutover.

3. **Older job validators are shallow.** `JOB_APPEND_TO_NOTE` and similar
   legacy validators check required-field presence only. New handlers
   (`LOG_SITE_ISSUE`, `ADD_PERSON`) have rigorous allowlists + enum
   validation. Worth bringing older validators up over time.

4. **No retention/compaction.** Flagged in original review, still open.
   `processed/`, `failed/`, `logs/`, vision sidecars — all grow forever.

5. **CouchDB config sprawl.** `127.0.0.1` hardcoded across registry,
   listener, ssh, couchdb_ops. Sibling env-var names use different
   patterns (`SSH_DEFAULT_REMOTE_HOST` vs. `BTQ_COUCHDB_REMOTE_HOST`).
   Extract to a dedicated config module before the Dell adds another
   deployment target.

## Dell-Readiness Assessment

**Not ready.** Substantial work required before deploying to a Linux box
with an NVIDIA GPU:

- Hardcoded macOS paths: iCloud directories, Homebrew (`/opt/homebrew/bin`),
  `~/Library/...`.
- `sys.platform == "darwin"` branches with no Linux equivalents in
  `project/queue_processor/watch.py:31` and transcription pipeline.
- LaunchAgent-only service definitions; no systemd units exist.
- No GPU/CUDA detection, no Ollama systemd story, no NVIDIA driver
  expectations documented.
- No deployment checklist or playbook for Dell (the existing
  `field-capture-production-deployment.md` covers the VPS SPA only).
- CouchDB config sprawl (above) compounds the deployment problem.

This is roughly the scope of roadmap Stage D plus the Dell-side parts of
Stage E. Hardware arriving makes it concrete and time-bounded.
